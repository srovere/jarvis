# Jarvis — Design

Date: 2026-11-23 · Status: draft for approval

## 1. Intent

The user develops several projects in parallel, each on a different development server, always working with Claude Code and asking it to "save progress to memory". Today the information needed to organize the day is scattered: Gmail, Google Calendar, Google Tasks and Claude Code memories spread across several servers.

Jarvis is an AI-driven personal assistant that:

1. Brings emails, events, tasks and projects together in one place and **links them to each other** through projects and people.
2. Shows a local **dashboard** (React) to read, act and ask an agent questions.
3. Knows, for each project, **what was last done, when, what comes next and what is pending**, and uses it to prepare meetings.
4. Exposes everything as its own **MCP server**, usable from Claude Code in the terminal and from the dashboard chat.

Explicit secondary goal: **learn to build agents** and practice MCP (server and client).

## 2. Constraints (non-negotiable)

- **Claude subscription only, never an Anthropic API key.** Every model call goes through the Claude Code CLI (`claude -p`), authenticated with the subscription token (`claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`). This rules out LangGraph, the Anthropic SDK and the Agent SDK.
- **Everything runs locally** with Docker Compose. Full control, no external hosting.
- **TypeScript** across the stack; **React** on the frontend; **PostgreSQL**.
- **Never send email.** Drafts only. The agent has no tool that sends.
- Credentials (Google OAuth, SSH keys, Claude token) outside the repo, mounted as secrets.
- **Extensibility with OOP and SOLID principles.** It starts with Google (Gmail, Calendar, Tasks), Claude Code and local/SSH access, but the code must be able to add other providers (e.g. Microsoft 365), other agents and other transports **without modifying the domain**: only by adding adapters (see §5.1).
- **Multi-account from the data model**: a single account is used at first, but every synced record belongs to an `account` (provider + identity).
- **Machine-independent**: Jarvis runs today on the user's local machine, but it must be movable to another one without code changes: everything host-specific (paths, ports, servers) is configuration and Docker volumes.
- **English only in the repository**: code, comments, user-facing strings, tests and documentation are written in English.

## 3. Goals, non-goals and anti-goals

**Goals (phase 1)**
- Registry of servers and projects with automatic discovery over SSH.
- Sync of Gmail (metadata + body on demand), Calendar and Tasks.
- Linking people↔projects, emails/events→projects (derived and manual), tasks→project (by Google Tasks list).
- Per-project highlights and a brief before each of the day's meetings, generated by Claude.
- Mirror of Google Tasks to `.jarvis/tasks.md` in the project's repo.
- MCP server with the domain tools.
- Dashboard: daily briefing, projects, emails, events, tasks, manual linking and chat with the agent.
- Store from day one the history needed for analytics.

**Phase 2 (out of scope now, but enabled by the design)**
- Analytics charts (see §9).
- Autonomous nightly agent that reads `.jarvis/tasks.md` on each server, analyzes requirements and writes proposals to `.jarvis/proposals/`.

**Non-goals**
- Sending emails, deleting emails, deleting or modifying other people's events, attachments.
- Access from outside the machine (phone, other computers), multi-user, user authentication.
- Two-way task sync with the repo.

**Anti-goals (failure even if it "works")**
- The agent being able to run arbitrary commands on the development servers.
- An action with an external effect (draft, event, task) happening without the user seeing and approving it when the agent proposes it from the chat.
- Any component requiring an Anthropic API key.
- Jarvis polluting the repos (commits, changes to `.gitignore`).

## 4. Approaches considered

| Approach | What it is | Why not / why |
|---|---|---|
| A. Claude Code + claude.ai connectors + dashboard as an Artifact | No own infrastructure | Rejected: the user wants everything local in Docker with full control; it cannot read remote memories over SSH. |
| B1. Own app + LangGraph.js + Claude API | Agent programmed as a graph | Rejected: requires an API key (violates the subscription constraint). |
| C. Minimal MCP server in Python (original spec drafted with Gemini) | 4 tools for Claude Code | Superseded by the current scope; its content (scopes, threaded drafts, logging) is reused. |
| **B2. Own app in Docker + own MCP server + headless Claude Code as the agent engine** | **Chosen** | Meets subscription-only, local, full control and learning MCP on both sides. |

## 5. Architecture

```
                  ┌─────────────── docker compose ───────────────────────────┐
browser ────────► │ web (React+Vite, nginx)                                    │
localhost:3000    │      │ REST/SSE                                            │
                  │      ▼                                                     │
                  │ api (NestJS) ──MCP client──► mcp-server (NestJS, Streamable HTTP)│
                  │      │                              │                      │
                  │      └─► claude -p ──MCP client─────┘                      │
                  │           (subscription)            ▼                      │
                  │ worker (jobs) ─────────────────► core ──► Google APIs      │
                  │      │                              │   ──► SSH to servers │
                  │      └─► claude -p (summaries)      ▼                      │
                  │                                  db (Postgres)             │
                  └────────────────────────────────────────────────────────────┘
Claude Code in the user's terminal ──MCP (HTTP, localhost)──► mcp-server
```

**Monorepo** (pnpm workspaces):

| Package | Responsibility |
|---|---|
| `packages/core` | Google clients (Gmail, Calendar, Tasks), restricted SSH client, DB access (Drizzle), domain logic (linking, free slots, email cleaning). No HTTP. |
| `packages/shared` | Types and Zod schemas shared between api, web and mcp-server. |
| `apps/mcp-server` | MCP server (official TS SDK, Streamable HTTP transport) on top of `core`. The only gateway for an **agent** to touch data. |
| `apps/api` | Dashboard backend. Reads/writes data **as an MCP client** of `mcp-server` (MCP client practice) plus its own endpoints for what is not a tool (manual linking, approvals, registry). Orchestrates the chat by launching `claude -p`. |
| `apps/worker` | Scheduled jobs: sync, SSH discovery, task mirror, summary generation with `claude -p`. Uses `core` directly. |
| `apps/web` | React + Vite. |
| `db` | Postgres 17 with a persistent volume. |

All ports are published on `127.0.0.1` only by default (configurable).

### 5.1 Extensibility architecture (ports and adapters)

The domain (`packages/core/domain`) defines **interfaces (ports)** and knows nothing about Google, Claude or SSH. Each integration is an **adapter** in its own package that implements those ports. One **composition root** per app (`apps/*/src/container.ts`) builds the dependencies from the configuration; nothing outside it does `new` on a concrete adapter.

| Port (segregated interfaces) | Initial adapter | Future |
|---|---|---|
| `MailReader`, `DraftWriter` | `GmailAdapter` | `OutlookAdapter` (Microsoft Graph) |
| `CalendarReader`, `EventWriter`, `FreeBusyProvider` | `GoogleCalendarAdapter` | `OutlookCalendarAdapter` |
| `TaskReader`, `TaskWriter` | `GoogleTasksAdapter` | `MicrosoftToDoAdapter` |
| `IdentityProvider` (own addresses, aliases) | `GmailSendAsIdentity` | Graph |
| `AuthFlow` (OAuth per provider) | `GoogleOAuthFlow` | `MicrosoftOAuthFlow` |
| `ProjectTransport` (named operations on a host: list projects, read file, stat, git log/status/remote, write under `.jarvis/`) | `LocalTransport` (host paths mounted into the container), `SshTransport` | others (e.g. a remote agent's API) |
| `AgentRunner` (run a prompt with allowed MCP tools, resumable session, streaming output) | `ClaudeCodeRunner` (`claude -p`, subscription) | another agent/CLI |
| `Summarizer` (highlights, meeting briefs, link suggestions, with schema-validated output) | `AgentSummarizer` on top of `AgentRunner` | — |
| Repositories (`ProjectRepository`, `EmailRepository`, …) | Drizzle/Postgres | — |

Principles applied:
- **S**: each class has one responsibility (e.g. `EmailCleaner`, `FreeSlotFinder`, `ThreadLinker`, `ProjectDiscoverer` are domain services separate from the adapters).
- **O**: new provider/transport/agent = new class + registration in a `ProviderRegistry`/`TransportRegistry`/`AgentRegistry`; the domain does not change.
- **L**: adapters fulfil the port's full contract; real differences between providers (Gmail threads vs Outlook conversations, task lists, aliases) are expressed through **declared capabilities** (`capabilities()`) that the domain queries, never with `instanceof`.
- **I**: separate read and write ports, so the chat/MCP can receive read-only access where appropriate.
- **D**: domain services depend on interfaces, injected through the constructor.

Domain types are provider-neutral (`MailThread`, `MailMessage`, `CalendarEvent`, `Task`, `Person`), and external IDs are stored as `(account_id, external_id)`. The provider's raw data goes into a JSONB column.

### 5.2 Machine independence

- Configuration in a `jarvis.config.yaml` file + environment variables (time zone, working hours, accounts, servers, AI cap); secrets in `secrets/`.
- Servers with `local` transport declare which host paths are mounted (e.g. `~/.claude/projects`, `/data/devel`) in `docker-compose.override.yml`, generated by `pnpm jarvis init` from the configuration. Moving Jarvis to another machine = copy config + secrets + Postgres volume (or restore a backup) and adjust the mounts.
- Scheduled jobs are **recoverable**: on startup (or when the machine wakes up), the worker detects missed runs (sync, 07:30 briefs) and runs them once, without duplicates.
- The MCP server listens on `127.0.0.1` by default; with `mcp.bind` and the bearer token it can be exposed (e.g. so that Claude Code sessions on remote servers use it through a reverse SSH tunnel). Not configured in phase 1, but the design does not prevent it.

## 6. Components in detail

### 6.1 Server and project registry

- **Server**: name, transport type (`local` | `ssh`), and its parameters (for `ssh`: host, port, user, key reference; for `local`: mounted paths and `home`). The machine Jarvis runs on uses `LocalTransport`; remote servers use `SshTransport`. Both implement `ProjectTransport`, so the rest of the system does not tell them apart.
- **Discovery**: for each server, list `~/.claude/projects/*`. Each folder corresponds to a directory where Claude Code was used; its name is the path with `/` replaced by `-` (reconstruction is ambiguous when the path contains dashes: verify candidates with `test -d`; if unresolved, ask for confirmation). For each valid path, get `git remote get-url origin`. The result is presented as **proposals** that the user confirms, edits or discards in the dashboard. Folders without a repo (e.g. `~`) are proposed flagged as "no repo".
- **Project**: name, server, path, GitHub repo, memory folder, list of **documents** (paths) with a type (`memory-project`, `memory-other`, `claude-md`, `spec`, `plan`, `readme`, `other`), and the linked Google Tasks list.
- **Automatically detected documents**: files in `memory/` (classified by the frontmatter `type`), `CLAUDE.md`, `README*`, `docs/superpowers/specs/*`, `docs/superpowers/plans/*` and paths mentioned in `type: project` memories. The user can add or remove documents by hand.

### 6.2 Restricted SSH access

- A dedicated key for Jarvis, mounted as a read-only secret; pinned `known_hosts` (new fingerprints are never accepted silently).
- The SSH client in `core` exposes **only named operations**, never a free-form command: `listClaudeProjects`, `readFile(path)` (only registered paths or inside the project/memory folder), `stat`, `gitLog(since)`, `gitStatus`, `gitRemote`, `writeJarvisFile(relPath, content)` (only under `<project>/.jarvis/`) and `ensureGitExclude` (adds `.jarvis/` to `.git/info/exclude`).
- Arguments validated and escaped; paths normalized and checked against the allowed prefix (no `..`, no symlinks outside the prefix).
- **Server-side restriction too** (Claude's decision): Jarvis's key is installed on each server with `command="~/.jarvis/jarvis-remote"` in `authorized_keys` (plus `no-port-forwarding,no-pty,no-agent-forwarding,no-X11-forwarding`). `jarvis-remote` is a small script, versioned in this repo, that only accepts the named operations above (it reads `SSH_ORIGINAL_COMMAND`) and rejects everything else. That way, not even whoever holds the key can run arbitrary commands. Deliverables: the script, its tests and a per-server installation procedure (`pnpm jarvis install-server <host>`).

### 6.3 Google sync

- **OAuth**: a "Desktop app" client in the user's own Google Cloud project. Scopes: `gmail.readonly`, `gmail.compose`, `calendar.events`, `tasks`. App in unverified *In production* mode (personal use) so the refresh token does not expire after 7 days. Initial flow with the `pnpm jarvis auth` command (loopback server). Tokens in a volume with 0600 permissions.
- **Gmail**: incremental sync by `historyId`. Metadata is stored (id, threadId, from, to, cc, subject, date, labels, snippet, whether the user replied in the thread). The **body is fetched on demand** and cleaned (HTML→text, no quoted text, no long signatures, truncated). Initial window: 90 days.
- **Calendar**: sync by `syncToken` of the user's calendars (configurable which ones count as "busy"). Stored: title, start, end, all-day, attendees, response status, video call link, source calendar.
- **Tasks**: lists and tasks (by `updatedMin`), with creation, due and completion dates.
- Default frequency: every 5 minutes (configurable). Network/quota errors: retry with backoff, without losing the cursor.

### 6.4 People and linking

- **People** are created from email addresses seen in emails and event attendees. The user links them to 0..N projects.
- **Emails**: project derived from the thread → from the thread's people (excluding the user). If it points to a single project, it is assigned; if it points to several, it stays as a **suggestion** with candidates and Claude proposes one from subject/content; the user confirms. Manual per-thread assignment always wins.
- **Events**: same criterion by attendees; manual assignment wins. An event can have 0..N projects.
- **Tasks**: 0..1 project, determined by the Google Tasks list (one list per project; the default list = no project). Changing project = moving to another list. When confirming a project, the registry allows **linking an existing list or creating a new one** named after the project (Claude's decision); lists without a project are shown as "unassigned".
- **Own addresses**: the user's addresses are obtained from Gmail's *send-as* configuration (aliases included) and are excluded from people-based linking; they also define "the user replied in the thread".

### 6.4.1 Priority emails (Claude's decision)

SQL query, no AI: threads with unread messages in the *Primary* category, or labelled IMPORTANT/STARRED, or **without a reply from the user** whose last message comes from a person linked to some project. Order: project-linked first, then by date. At most 10 in the briefing.

### 6.5 Task mirror to the repo

- One direction only: Google Tasks → `<project>/.jarvis/tasks.md` on the project's server. It is fully regenerated when that list's tasks change.
- `.jarvis/` is excluded via `.git/info/exclude`; Jarvis never commits or touches `.gitignore`.
- Format: Markdown readable by humans and by Claude, with frontmatter (`project`, `generated_at`, `source: google-tasks`) and one section per task (Google id, title, status, due date, notes). The nightly agent (phase 2) will write to `.jarvis/proposals/` and never to `tasks.md`.

### 6.6 Project highlights and meeting briefs

- The worker takes a **copy** of each registered document (content + hash + mtime) and of the recent `git log`. If any hash changed, it enqueues highlight regeneration.
- **Highlights** (per project): `last_work` (what and when), `next_steps`, `pending/blockers`, `references` (cited documents). Generated by `claude -p` with JSON output validated against a schema; versioned (history).
- **Pre-meeting brief**: every morning (and when a new event for the day is synced) for events linked to projects: project highlights + recent email threads with the attendees + the project's open tasks → a short "get up to speed before the meeting" text.
- Every `claude -p` invocation runs with tools disabled or limited to read-only, a fixed prompt, and external content marked as untrusted data.
- **Careful use of the subscription** (Claude's decision): every background AI job goes through a single queue with concurrency 1, *debounce* (a project is regenerated at most once every 2 hours even if it changes several times), a **configurable daily cap** (default 40 invocations) and a preferred window (meeting briefs generated at 07:30; highlights outside that time only if something changed). If the cap is reached, work is deferred to the next day and the dashboard says so. The interactive chat does not count towards the cap. Each invocation is recorded (duration, reason) to allow tuning.

### 6.7 MCP server

Streamable HTTP transport on `127.0.0.1`, with a shared local bearer token (so that another process on the machine cannot use it without permission). Tools (indicative names; the builder may adjust):

| Tool | Type |
|---|---|
| `get_daily_briefing(date_offset_days)` | read: the day's events with pre-meeting brief, priority emails, tasks due, highlights of active projects |
| `search_emails(query, max_results)` / `read_thread(thread_id)` | read (native Gmail syntax; clean, truncated body) |
| `list_events(range, project?)` | read |
| `list_tasks(project?, status?)` | read |
| `list_projects()` / `get_project_status(project)` | read |
| `find_free_slot(duration_minutes, preferred_start_hour?)` | read |
| `create_gmail_draft(to?, subject, body, thread_id?, cc?)` | write |
| `block_focus_time(task_name, duration_minutes, preferred_start_hour?, project?)` | write |
| `create_task(title, notes?, due?, project?)` / `complete_task(task_id)` | write |
| `link_entity(kind, id, project)` | write (local) |

Rules:
- **Drafts**: if there is a `thread_id`, `to` is optional (defaults to the sender of the last message), subject `Re:` and `In-Reply-To`/`References` headers copied from the last message. There is never a send tool.
- **Focus block**: finds the next free slot within working hours (default 09:00–19:00, Monday to Friday, `America/Argentina/Buenos_Aires`, all configurable) over the next 5 work days, treating events in the configured calendars as busy. Title `[Focus] {task_name}`. If a `[Focus] {task_name}` already exists that same day, it does not duplicate: it reports it.
- Structured responses (`structuredContent` + short text). Email content is marked as external/untrusted.
- Logs to stderr / structured logger; never complete sensitive data in logs.

### 6.8 Dashboard chat (agent)

- `api` launches `claude -p --output-format stream-json` with `--mcp-config` pointing at `mcp-server`, `--allowedTools` limited to Jarvis's MCP tools (no Bash, no file editing), and `--resume <session>` to continue conversations. Output is streamed to the browser over SSE.
- **Action approval**: in the chat, write tools are not executed directly. The agent uses a `propose_action(kind, params, rationale)` tool that records a pending action; the dashboard shows it with an **Approve / Discard** button, and on approval `api` runs the real tool through MCP. (From Claude Code in the terminal, write tools are subject to Claude Code's normal permissions.)
- The agent configuration (instructions, skills, permissions) is versioned in the repo (`agent/`); it is part of the learning.
- The `api` container ships the Claude Code CLI; `CLAUDE_CODE_OAUTH_TOKEN` as a secret.

### 6.9 Dashboard (web)

Views:
- **Today**: agenda with a brief per meeting, priority emails, tasks due, focus blocks.
- **Projects**: list with highlights, last activity and a simple traffic light; detail with linked documents, people, threads, events and tasks.
- **Emails / Events / Tasks**: lists filterable by project, with manual linking and suggestions pending confirmation.
- **People**: link people to projects.
- **Registry**: servers and discovery proposals.
- **Chat**: persistent side panel with actions pending approval.
- Direct actions: complete task, create task in a project, block focus time, open/create draft (opens in Gmail), link/unlink.

### 6.10 Data model (conceptual)

`accounts` (provider, identity, credentials reference, capabilities), `servers` (transport type + parameters), `projects`, `project_documents` (+ `document_snapshots` with hash, mtime, content), `project_highlights` (versioned), `people`, `person_projects`, `email_threads`, `emails` (metadata), `thread_projects` (origin: derived/suggested/manual), `calendars`, `events`, `event_projects` (origin), `meeting_briefs`, `task_lists` (→ project), `tasks` (with `created_at`, `completed_at`), `commits` (project, hash, date, author, message), `sync_state` (cursors), `chat_sessions`, `pending_actions`, `discovery_proposals`. Google's raw data is also stored in a JSONB column so no fields are lost.

## 7. Security

- Minimal Google scopes; no `mail.google.com`.
- No email send tool; chat actions require explicit approval.
- SSH with named operations and bounded paths; no arbitrary execution.
- Email and document content treated as untrusted in every prompt.
- Secrets (OAuth client, tokens, SSH key, Claude token, MCP token) in `secrets/` outside git (`.gitignore`) and mounted as Docker secrets; `.env.example` documents what is needed.
- Ports on `127.0.0.1` only.

## 8. Testing

- **Per-port contract tests**: a shared suite that every adapter of a port must pass (today against doubles and simulated Google; tomorrow against Microsoft), guaranteeing substitutability (the L in SOLID).
- Unit tests (Vitest) for `core` logic: email cleaning, free slot computation, linking, path reconstruction, SSH path validation, building drafts with reply headers.
- Integration with **simulated** Google APIs and SSH (without touching the real account).
- MCP server tests with the SDK's MCP client.
- `claude -p` is abstracted behind an interface so it can be simulated in tests.

## 9. Analytics (phase 2) — data stored from phase 1

Agreed initial set: (1) hours per project per week (meetings vs focus), (4) tasks created vs completed per week, (5) open tasks by age, (8) commit heatmap, (9) days since last activity, (12) response time to clients / threads awaiting reply, (14) health traffic light per project. The model in §6.10 stores what is needed for these and for the rest of the catalogue discussed (burndown, task cycle time, email volume, meetings per client).

## 10. Google Cloud setup (summary; the details go in the README)

1. Create a project in the Google Cloud Console.
2. Enable Gmail API, Google Calendar API and Google Tasks API.
3. Consent screen: type *External*, add the 4 scopes, add your own address as a test user and then **publish to production** (unverified, personal use) to avoid the 7-day expiry.
4. Credentials → OAuth client ID → *Desktop app*; download the JSON to `secrets/google-oauth-client.json`.
5. `pnpm jarvis auth` to generate the initial token.

## 11. Decisions made by Claude (open to revision)

- **NestJS** for `api`, `mcp-server` and `worker` (delivery layer: modules, controllers, dependency injection, `@nestjs/schedule` for jobs). The domain in `packages/core` is pure TypeScript, without NestJS dependencies; adapters are registered in Nest modules through injection tokens that point to the ports.
- **Drizzle** as the ORM, used only inside the repository classes that implement the persistence ports (the domain never sees it). Chosen over Prisma/MikroORM for being lightweight, typed and with explicit SQL; changing it only affects the repositories.
- pnpm workspaces, Vitest.
- Local machine with `LocalTransport` (mounted paths), remote ones with `SshTransport`.
- Server-side SSH restriction with `jarvis-remote` (forced command).
- Priority emails by SQL rules, no AI.
- Daily cap of 40 background AI invocations, 2 h debounce per project, meeting briefs at 07:30.
- Google Tasks lists: link an existing one or create one when registering a project.
- MCP on `127.0.0.1` only in phase 1; exposure to remote sessions is prepared, not configured.
- Jobs recoverable after shutdown/suspend.
- `.jarvis/` excluded via `.git/info/exclude`.
- Focus block: 5 work days ahead, Mon–Fri 09–19.
- Initial Gmail window: 90 days; sync frequency 5 minutes.
- Chat action approval through `propose_action`.
- `api` accesses data as an MCP client (client practice) except for admin functions.
